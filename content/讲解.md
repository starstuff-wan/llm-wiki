## 1. Huffman 编码：这一步是作业的核心

### 1.1 原理一句话

**出现次数多的像素给短码，出现次数少的给长码**，并且任何码字都不能是另一个码字的前缀（前缀码），这样解码时不用分隔符也不会歧义。

### 1.2 建树（`HuffTable::build`，`huffman.cpp:54`）

1. 每个出现过的像素值做一个叶子结点，权重 = 出现次数；
2. 反复取出**权重最小的两个**结点，合并成一个新父结点（权重相加），塞回队列；
3. 最后剩下一个结点就是根；
4. 从根往下走，**左边记 0、右边记 1**，走到叶子时经过的 0/1 序列就是该像素的码字。

代码里用的是 **小根堆**（`std::priority_queue` + 自定义比较器 `HNodeGreater`），每次取最小是 O(log n)，总共 O(n log n)。

> **答辩点**：为什么用堆而不是每次扫一遍数组找最小？——256 个符号时差别不大，但堆是标准做法，且符号数增大时优势明显。

### 1.3 为什么用“规范 Huffman”（`HuffTable::buildCanonical`，`huffman.cpp:29`）

普通 Huffman 每个结点都存码字，压缩文件里就得写 256 个码字（每个 4 字节）＝ 1024 字节开销。

**规范 Huffman 只存码长**（256 个字节），码字按固定规则现算：

```
按码长从小到大、同长度按符号从小到大排序
code = 0
for 每个长度 L:
    code = (code + 长度小于 L 的码字个数) << 1
    该长度的码字从这里依次 +1 分配
```

解码端用**同样的规则**重建，所以两边码字必然一致。文件头因此只有 256 字节。

> **答辩点**：这是本题最容易被追问的地方——“你怎么保证解码端码字和编码端一致？”答：不传码字，只传码长，码字由确定性算法推导。

### 1.4 比特流（`BitWriter::put`，`huffman.cpp:159`）

Huffman 输出的是**不等长比特**，但文件是按字节写的，所以要自己攒位：

```cpp
void BitWriter::put(uint32_t value, int nbits) {
    for (int i = nbits - 1; i >= 0; --i) {     // 高位先写（MSB first）
        uint32_t bit = (value >> i) & 1u;
        if ((bitCount & 7u) == 0) buf.push_back(0);   // 满 8 位换新字节
        if (bit) buf.back() |= (0x80u >> (bitCount & 7u));
        ++bitCount;
    }
}
```

最后一次写入不满 8 位时，低位补 0。因此**必须记录有效比特数**，否则解码会把补的 0 当成数据——这就是文件头第 24 字节那 8 个字节 `payloadBits` 的用途。

### 1.5 解码（`huffmanDecode`，`huffman.cpp:211`）

没有分隔符，怎么知道码字在哪结束？**逐位读，每读一位就查一次表**：

```cpp
code = (code << 1) | nextBit;
if (表里有 (当前长度, code)) { 输出该符号; break; }
```

因为前缀码保证“短码不会是长码的前缀”，一旦命中就不可能再是别的符号。

代码里用 `unordered_map<uint64_t,int>`，键是 `(长度 << 32) | 码字`，避免长短码混淆。

## 2. 压缩文件格式（`main.cpp` 的 `writeIcp` / `readIcp`）

```
偏移  长度  含义
0     4     魔数 "ICP1"
4     1     算法编号 0=Huffman 1=RLE 2=LZW
5     1     通道数 1=灰度 3=彩色
6     2     保留
8     4     图像宽度
12    4     图像高度
16    4     原始字节数
20    4     载荷长度
24    8     载荷有效比特数
32    -     载荷
```

载荷按算法不同：

* **Huffman**：`256 字节码长表` + `比特流`
* **RLE**：命令流（控制字节 + 数据）
* **LZW**：12 位定长码流

> **答辩点**：为什么文件头要存“原始字节数”？——解码时要知道该还原多少个像素，否则末尾补的 0 会被误解。

## 3. RLE（行程长度编码）

**原理**：一行里连续相同的像素很多时，不存 N 个像素，改存“值 + 重复次数”。

命令字节 `c`：

* `c & 0x80`：后面跟 1 个字节，重复 `c & 0x7F` 次（游程）
* 否则：后面跟 `c` 个原始字节（字面段）

代码在 `rleEncode`（`huffman.cpp:263`）/ `rleDecode`（`huffman.cpp:290`）。**为什么需要字面段**？因为照片里相邻像素很少完全相同，如果每个像素都写成“重复 1 次”，反而变大——字面段用于把不重复的像素打包存。

> 实测：BMP 照片类图像用 RLE 会**变大**（2064000 → 2079434），这是正常现象，正好可以在报告里当作对比分析。

## 4. LZW

**原理**：边压缩边建字典，把“出现过的长串”映射成一个编号。

```
字典初始 = 256 个单字节
读入字符，若 前缀+当前字符 在字典里 → 前缀变长，继续
否则 → 输出前缀的编号，把 前缀+当前字符 登记为新编号
```

关键细节，也是本题最容易写错的地方：

1. **字典里只放两字节及以上的串**。若把单字节也放进去，键 `(前缀<<8)|字节` 会和单字节的键撞车（我第一版就踩了这个坑）。
2. **编解码两端的词条登记时机必须一致**：编码器每输出一个码字就登记一个新词条；解码器每读一个码字，用“上一个串 + 当前串首字节”补登一个。差一步就全乱。
3. 本实现**固定 12 位码**，不去维护“字典满了位宽何时从 9 涨到 10”。代价是压缩比略差（约 5%~10%），好处是不会有位宽不同步的 bug。

> **答辩点**：老师很可能问“LZW 为什么能压缩？”——因为它把重复出现的**串**换成了短编号，而编号的比特数（12 位）远小于串的长度。

## 5. 图像读写（`image.cpp`）

不调用任何图像库，自己按 BMP 规范解析：

* **BITMAPFILEHEADER 14 字节**：`'B''M'` + 文件大小 + 像素数据偏移
* **BITMAPINFOHEADER 40 字节**：宽、高、位深、压缩方式
* **像素数据**：**自下而上**存放，每行按 4 字节对齐，24 位时是 `B,G,R` 顺序

三个容易错的地方，代码里都处理了：

1. **行对齐**：每行字节数要补到 4 的倍数，`stride = (width*3 + 3) & ~3`；
2. **自下而上**：BMP 默认最后一行在最前面，读的时候要倒过来；`height` 为负表示自上而下；
3. **BGR 顺序**：BMP 存的是 B,G,R，程序内部统一用 R,G,B。

## 6. 性能指标（`psnr` / `ssim` / `entropyPerSymbol`）

* **压缩比** = 原始字节数 / 压缩后字节数（含 32 字节文件头）
* **PSNR** = `10·log10(255² / MSE)`，无损压缩时 MSE=0，程序里约定输出 99 表示无穷
* **SSIM**：8×8 窗口上算均值、方差、协方差，用 `C1=(0.01·255)²`、`C2=(0.03·255)²` 稳定分母
* **一阶熵**：`-Σ p·log2(p)`，是 Huffman 的**理论下限**。报告里把“平均码长”和“熵”并列，能说明 Huffman 的效率（一般差距 < 0.1 bit）

## 10. 常见追问速查

| 问题 | 一句话答案 |
|---|---|
| Huffman 为什么能保证前缀码？ | 码字只出现在叶子，从根到叶的路径不会互相包含 |
| 为什么不用固定 8 位？ | 频率不均时，短码能省下的比长码多花的更多（熵 < 8） |
| 压缩后为什么反而变大？ | 熵接近 8（随机噪声），加上文件头开销 |
| RLE 适合什么图？ | 大片同色，如扫描文档、图标；不适合照片 |
| LZW 和 Huffman 谁强？ | 图上纹理重复多时 LZW 强（实测 14 万 vs 67 万）；纯频率偏斜时 Huffman 强 |
| 无损能不能再压？ | 能：先 LZ 再 Huffman（DEFLATE 思路），本程序留作扩展 |
