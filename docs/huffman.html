核心原理

Huffman 编码

1.1 原理一句话

出现次数多的像素给短码，出现次数少的给长码，并且任何码字都不能是另一个码字的前缀（前缀码），这样解码时不用分隔符也不会歧义。

1.2 建树（HuffTable::build，huffman.cpp:54）

  1. 每个出现过的像素值做一个叶子结点，权重 = 出现次数；
  2. 反复取出权重最小的两个结点，合并成一个新父结点（权重相加），塞回队列；
  3. 最后剩下一个结点就是根；
  4. 从根往下走，左边记 0、右边记 1，走到叶子时经过的 0/1 序列就是该像素的码字。

代码里用的是 小根堆（std::priority_queue + 自定义比较器 HNodeGreater），每次取最小是 O(log n)，总共 O(n log n)。

💡

答辩点：为什么用堆而不是每次扫一遍数组找最小？——256 个符号时差别不大，但堆是标准做法，且符号数增大时优势明显。

1.3 为什么用“规范 Huffman”（HuffTable::buildCanonical，huffman.cpp:29）

普通 Huffman 每个结点都存码字，压缩文件里就得写 256 个码字（每个 4 字节）＝ 1024 字节开销。

规范 Huffman 只存码长（256 个字节），码字按固定规则现算：

text
按码长从小到大、同长度按符号从小到大排序
code = 0
for 每个长度 L:
    code = (code + 长度小于 L 的码字个数) << 1
    该长度的码字从这里依次 +1 分配

解码端用同样的规则重建，所以两边码字必然一致。文件头因此只有 256 字节。

💡

答辩点：这是本题最容易被追问的地方——“你怎么保证解码端码字和编码端一致？”答：不传码字，只传码长，码字由确定性算法推导。

1.4 比特流（BitWriter::put，huffman.cpp:159）

Huffman 输出的是不等长比特，但文件是按字节写的，所以要自己攒位：

cpp
void BitWriter::put(uint32_t value, int nbits) {
    for (int i = nbits - 1; i >= 0; --i) {     // 高位先写（MSB first）
        uint32_t bit = (value >> i) & 1u;
        if ((bitCount & 7u) == 0) buf.push_back(0);   // 满 8 位换新字节
        if (bit) buf.back() |= (0x80u >> (bitCount & 7u));
        ++bitCount;
    }
}

最后一次写入不满 8 位时，低位补 0。因此必须记录有效比特数，否则解码会把补的 0 当成数据——这就是文件头第 24 字节那 8 个字节 payloadBits 的用途。

1.5 解码（huffmanDecode，huffman.cpp:211）

没有分隔符，怎么知道码字在哪结束？逐位读，每读一位就查一次表：

cpp
code = (code << 1) | nextBit;
if (表里有 (当前长度, code)) { 输出该符号; break; }

因为前缀码保证“短码不会是长码的前缀”，一旦命中就不可能再是别的符号。

代码里用 unordered_map<uint64_t,int>，键是 (长度 << 32) | 码字，避免长短码混淆。
